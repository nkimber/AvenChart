From generation to evaluation

A deliberate pause to understand the code.

Phase 1 established that coding agents could produce a broad, functioning reimplementation of a mature healthcare application. Phase 2 asks a different question: is the result understandable, safe, maintainable, efficient, and structurally sound enough to justify continued investment?

Phase 1 is now historical. Its source revision, measurements, and approximately 86% functional-coverage estimate are fixed and will not be revised as later work changes the application.

Evidence rules

The baseline remains fixed.

The Phase 1 tabs read from a generated dataset pinned to one exact source revision. Running the history generator again produces the same Phase 1 record even after new commits are added to the repository.

  • Later fixes do not increase the Phase 1 coverage estimate or change its historical metrics.
  • Phase 2 findings describe the Phase 1 baseline and cite concrete evidence from that snapshot.
  • Future phases receive their own status and evidence instead of being folded into Phase 1.

Phase 01 · Experimental build · Closed

Can an agent rebuild a mature application?

AvenChart tested whether autonomous coding agents could recreate and modernize the behavior of an established EHR and practice-management product on a new technology stack. OpenEMR supplied the functional benchmark; the retained AvenChart application code was produced by coding agents.

This was a functional reimplementation, not a line-by-line translation. OpenEMR source was used to understand product behavior and workflows, not as code to port.

Estimated functional coverage at closure was approximately 86%. Most of the remaining gap was concentrated in security capabilities and external integrations. This estimate is retained as a Phase 1 observation, not a certification of correctness or completeness.

The experiment

Generation came before evaluation.

The Phase 1 objective was broad functional reconstruction, one behavior slice at a time, under an unusual autonomy constraint.

OpenEMR was selected because it is a mature, extensively used open-source EHR and practice-management application. Its breadth and real-world functionality made the autonomy test demanding enough to be meaningful.

Core experimental constraint Zero human-authored application code.

The human role was limited to setting direction and objectives. That constraint makes Phase 1 useful as an experiment, but it also means the output now requires deliberate human-oriented critique before it can be trusted as an engineering foundation.

Generation pass 01

Functional baseline

Agents created an ASP.NET Core API, PostgreSQL data model, migrations, verification scripts, and a utilitarian React reference interface while working through OpenEMR functionality slice by slice.

Generation pass 02

Interface modernization

A second agent produced a more polished React and TypeScript clinician and portal interface against the same API and data foundation. Both generation passes belong to the Phase 1 experiment.

What Phase 1 does not claim

Functional breadth does not establish architectural quality, clinical safety, privacy, security, performance, maintainability, accessibility, regulatory readiness, or production fitness. Those are explicit subjects of Phase 2, not conclusions imported into this historical record.
