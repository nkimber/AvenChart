From generation to evaluation

A deliberate pause to understand the code.

Phase 1 established that coding agents could produce a broad, functioning reimplementation of a mature healthcare application. Phase 2 asks a different question: is the result understandable, safe, maintainable, efficient, and structurally sound enough to justify continued investment?

Phase 1 is now historical. Its source revision, measurements, and approximately 86% functional-coverage estimate are fixed and will not be revised as later work changes the application.

Evidence rules

The baseline remains fixed.

The Phase 1 tabs read from a generated dataset pinned to one exact source revision. Running the history generator again produces the same Phase 1 record even after new commits are added to the repository.

  • Later fixes do not increase the Phase 1 coverage estimate or change its historical metrics.
  • Phase 2 findings describe the Phase 1 baseline and cite concrete evidence from that snapshot.
  • Future phases receive their own status and evidence instead of being folded into Phase 1.

Phase 01 · Experimental build · Closed

Can an agent rebuild a mature application?

AvenChart tested whether autonomous coding agents could recreate and modernize the behavior of an established EHR and practice-management product on a new technology stack. OpenEMR supplied the functional benchmark; the retained AvenChart application code was produced by coding agents.

This was a functional reimplementation, not a line-by-line translation. OpenEMR source was used to understand product behavior and workflows, not as code to port.

Estimated functional coverage at closure was approximately 86%. Most of the remaining gap was concentrated in security capabilities and external integrations. This estimate is retained as a Phase 1 observation, not a certification of correctness or completeness.

The experiment

Generation came before evaluation.

The Phase 1 objective was broad functional reconstruction, one behavior slice at a time, under an unusual autonomy constraint.

OpenEMR was selected because it is a mature, extensively used open-source EHR and practice-management application. Its breadth and real-world functionality made the autonomy test demanding enough to be meaningful.

Core experimental constraint Zero human-authored application code.

The human role was limited to setting direction and objectives. That constraint makes Phase 1 useful as an experiment, but it also means the output now requires deliberate human-oriented critique before it can be trusted as an engineering foundation.

Generation pass 01

Functional baseline

Agents created an ASP.NET Core API, PostgreSQL data model, migrations, verification scripts, and a utilitarian React reference interface while working through OpenEMR functionality slice by slice.

Generation pass 02

Interface modernization

A second agent produced a more polished React and TypeScript clinician and portal interface against the same API and data foundation. Both generation passes belong to the Phase 1 experiment.

What Phase 1 does not claim

Functional breadth does not establish architectural quality, clinical safety, privacy, security, performance, maintainability, accessibility, regulatory readiness, or production fitness. Those are explicit subjects of Phase 2, not conclusions imported into this historical record.

    Phase 02 · Assessment and planning · In progress

    Critically assess what Phase 1 produced.

    Phase 2 converts a broad functional experiment into an evidence-based engineering decision. It asks whether the generated system is coherent, understandable, secure, safe, efficient, testable, and maintainable—and identifies what must change before continued development is justified.

    This phase produces analysis and recommendations. It does not improve the application while the assessment is still establishing what the real problems are and how they relate to one another.

    Phase 02 status In progress

    Assessment setup and baseline preservation

    Started August 20, 2026

    Phase charter

    A decision phase, not a refactoring sprint.

    The purpose is to replace impressions with a traceable account of the codebase’s strengths, risks, liabilities, and opportunities.

    Primary question
    Is this a sound foundation for a maintainable healthcare product?
    Entry condition
    Phase 1 source and measurements fixed at one revision
    In scope
    The complete solution, its runtime behavior, tests, data, operations, and documentation
    Out of scope
    Unapproved modernization work and claims of production readiness
    Exit condition
    Coverage is complete, findings are validated, and recommendations are ordered and accepted
    Decision output
    Proceed, proceed conditionally, reduce scope, replace components, or stop

    Required deliverables

    The assessment must leave a usable body of evidence.

    Phase 2 is complete only when another engineer can understand what was examined, reproduce the most important conclusions, and see why the proposed sequence of work follows from the findings.

    01

    Current-state architecture

    System boundaries, dependencies, data flows, deployment shape, and cross-cutting services as they actually exist.

    02

    Assessment coverage matrix

    Every subsystem and quality domain, its review status, evidence sources, reviewer, and any justified exclusions.

    03

    Quality scorecard

    A concise view of strengths, weaknesses, uncertainty, and production-blocking conditions without hiding nuance.

    04

    Validated findings register

    Evidence-backed problems and opportunities with severity, reach, cause, risk, and affected components.

    05

    Recommendation catalog

    Target states, benefits, prerequisites, complexity, risk, acceptance criteria, and alternatives for each proposal.

    06

    Dependency-aware roadmap

    An implementation order that addresses blockers first and avoids spending effort on work likely to be displaced.

    Assessment flow

    From inventory to an approved roadmap.

    1. 01

      Inventory

      Map projects, modules, routes, persistence, integrations, tests, and runtime boundaries.

    2. 02

      Assess

      Apply the same quality model to every subsystem and record both evidence and uncertainty.

    3. 03

      Validate

      Confirm important findings through tests, traces, measurements, and cross-component review.

    4. 04

      Recommend

      Describe target states and measurable benefits, including cost, prerequisites, and alternatives.

    5. 05

      Decide

      Accept, defer, reject, or combine recommendations and approve the Phase 3 sequence.

    Operating principles

    Evidence before preference.

    • Assess the system that exists, not the architecture its names imply.
    • Separate production blockers from ordinary maintainability and style concerns.
    • Distinguish isolated defects from repeated patterns and systemic causes.
    • Do not recommend a fashionable pattern without a demonstrated problem and measurable benefit.
    • Record uncertainty explicitly when evidence is incomplete or behavior cannot yet be reproduced.

    Phase 02 · Assessment framework

    Review every quality dimension consistently.

    The framework prevents the review from becoming a collection of isolated code comments. Each domain is evaluated across the complete solution using observable evidence, and each conclusion records what was examined, what remains uncertain, and how much of the system it affects.

    Assessment domains

    Twelve lenses on one system.

    A domain is complete only after its relevant backend, frontend, database, runtime, and verification surfaces have been considered. All domains begin unassessed; status changes only with recorded evidence.

    01Not assessed

    Architecture and boundaries

    Project responsibilities, dependency direction, modularity, coupling, cohesion, and cross-cutting ownership.

    • Dependency and flow maps
    • Boundary violations
    • Change-impact sampling
    02Not assessed

    Code structure and readability

    Naming, file and method size, organization, duplication, complexity, conventions, and human traceability.

    • Complexity and duplication scans
    • Representative code tracing
    • Convention consistency
    03Not assessed

    Domain correctness and clinical safety

    Business invariants, lifecycle rules, error states, clinical consequences, and protection against unsafe ambiguity.

    • Workflow-to-code tracing
    • Invariant and edge-case tests
    • Safety-critical failure review
    04Not assessed

    Data and persistence

    Schema quality, transaction boundaries, consistency, concurrency, ORM and SQL use, migrations, retention, and recovery.

    • Query and transaction review
    • Migration replay
    • Concurrency scenarios
    05Not assessed

    Security, privacy, and access control

    Identity, authorization, secrets, input trust, auditability, sensitive-data handling, isolation, and misuse resistance.

    • Trust-boundary mapping
    • Authorization-path sampling
    • Secret and data-flow review
    06Not assessed

    Performance and scalability

    Latency, query behavior, allocation, payload size, contention, caching, background work, and expected operating limits.

    • Hot-path and query analysis

    07Not assessed

    • Failure injection

    Evidence standard

    Every conclusion must be traceable.

    Observe

    Concrete condition

    Name the behavior, structure, or absence that was actually found.

    Locate

    Reproducible evidence

    Link the code, configuration, trace, query plan, test, or measured scenario.

    Interpret

    Consequence and reach

    Explain why it matters, who or what is affected, and whether it is isolated or systemic.

    Calibrate

    Confidence and uncertainty

    Record what supports the conclusion and what remains unknown or untested.

    Finding severity

    Priority reflects consequence, not annoyance.

    Severity combines plausible impact, likelihood, affected population, detectability, and blast radius. Effort is recorded separately so a difficult problem is not mistaken for a low-priority problem.

    Blocker

    Could make clinical or production use unacceptable; must be resolved or explicitly accepted before release.

    High

    Material correctness, security, privacy, reliability, or systemic maintainability risk requiring early action.

    Medium

    Meaningful localized risk or recurring cost that should be planned but does not independently block all progress.

    Low

    Contained defect, inconsistency, or inefficiency with limited consequence and straightforward workarounds.

    Opportunity

    Optional improvement with measurable value but no demonstrated defect or unmanaged risk.

    Completion rule

    “Reviewed” must mean something.

    • All in-scope subsystems are mapped to every applicable assessment domain.
    • Each coverage item records evidence, status, reviewer, date, and unresolved uncertainty.
    • High-severity and systemic findings have been independently reproduced or corroborated.
    • Excluded areas are named with a reason, risk statement, and follow-up decision.
    • The findings register and scorecard agree with the underlying evidence.

    Phase 02 · Findings register

    Record what the evidence supports.

    Findings are the durable analytical output of the review. A finding is not a preference, a proposed solution, or a vague concern: it is a reproducible condition with a stated consequence, affected scope, severity, and confidence level.

    0validated findings

    Register status

    The register begins empty by design.

    Phase 1 observations and assumptions are inputs to the review, not pre-approved findings. Entries will appear here only after the relevant evidence has been captured and the consequence has been evaluated.

    Assessment setup

    Finding record

    One schema for every quality domain.

    Consistent fields make findings comparable, searchable, reviewable, and suitable for turning into recommendations without losing the evidence that justified them.

    FieldPurposeRequired content
    Identifier and titleStable referenceDomain prefix, sequence, and a precise condition—not a proposed fix
    ConditionWhat existsThe behavior, structure, omission, or repeated pattern observed
    EvidenceReproducibilityFiles, lines, tests, traces, measurements, requests, plans, or screenshots
    ConsequenceWhy it mattersImpact on users, patients, data, operations, delivery, or future change
    Cause and reachSystem contextLikely cause, affected components, frequency, and isolated versus systemic classification
    RiskPriority inputSeverity, likelihood, blast radius, detectability, confidence, and production-blocker status
    DispositionGovernanceOpen, validated, disputed, accepted risk, addressed, superseded, or closed

    Finding lifecycle

    From observation to accepted evidence.

    1. Observed

      A potential condition is captured with its initial location and context.

    2. Reproduced

      The condition is confirmed through a second path, executable scenario, or corroborating evidence.

    3. Analyzed

      Cause, reach, consequence, severity, confidence, and uncertainty are recorded.

    4. Validated

      The finding is reviewed for accuracy, duplication, proportionality, and systemic implications.

    5. Dispositioned

      It is linked to a recommendation, accepted as risk, deferred, disputed, or closed with rationale.

    Analytical boundary

    Context is not a finding.

    The approximately 86% coverage estimate, the GenAI-only creation method, and known functional gaps explain why the assessment exists. They do not prove that any particular architecture, subsystem, or implementation is poor.

    Likewise, modern syntax, an ORM, a test suite, or a named architectural pattern does not prove quality. Phase 2 evaluates whether each choice works in this system and whether its actual consequences are acceptable.

    Phase 02 · Recommendations

    Turn findings into an ordered decision.

    A recommendation describes a justified change in direction or target state. It must identify the problem it addresses, the value it creates, the evidence that will prove success, and the dependencies and risks that determine when—or whether—it should be implemented.

    Recommendation record

    A proposal must explain more than the desired technology.

    Recommendations are written so they can be accepted, deferred, rejected, combined, or implemented without reconstructing the original argument from memory.

    Problem

    Linked findings

    The validated conditions, risks, and root causes this proposal addresses.

    Direction

    Target state

    The intended structure or behavior, including what will remain unchanged.

    Value

    Expected benefit

    Risk reduction, correctness, safety, performance, clarity, cost, or delivery improvement.

    Sequence

    Dependencies

    Prerequisites, unlocked work, conflicts, migration order, and decisions that must come first.

    Effort

    Size and complexity

    Estimated breadth, technical difficulty, coordination, migration needs, and specialist involvement.

    Risk

    Change exposure

    Regression surface, data risk, operational impact, reversibility, and rollout strategy.

    Proof

    Acceptance criteria

    Observable outcomes and tests that distinguish completion from partial implementation.

    Choice

    Alternatives and disposition

    Viable alternatives, do-nothing consequences, and the accept, defer, reject, or combine decision.

    Default ordering logic

    Protect the system before polishing it.

    The final roadmap will follow actual dependencies, but it begins with a risk-first bias so attractive cleanup does not displace safety, correctness, security, privacy, or recoverability work.

    1. 01

      Production and safety blockers

      Conditions that make deployment or clinical reliance unacceptable.

    2. 02

      High-risk correctness, security, and privacy

      Material exposure that can be addressed without waiting for broader redesign.

    3. 03

      Foundational architecture and boundaries

      Changes that reduce systemic coupling and make later work safer and smaller.

    4. 04

      Data, performance, and operational resilience

      Measured bottlenecks, consistency risks, failure recovery, and capacity constraints.

    5. 05

      Maintainability and duplication

      Repeated implementation cost, excessive bulk, unclear ownership, and difficult change paths.

    6. 06

      Developer experience and stylistic consistency

      Tooling, conventions, documentation, and refinements that compound future delivery quality.

    Sizing language

    Size and difficulty remain separate from value.

    S

    Contained

    One component or narrow behavior; minimal migration and coordination.

    M

    Multi-file or multi-layer

    Several related components with meaningful regression coverage and review.

    L

    Cross-cutting

    Multiple subsystems, data or contract migration, staged rollout, or broad verification.

    XL

    Program-level

    Architectural transition requiring decomposition, milestones, coordination, and explicit rollback strategy.

    Phase 2 exit gate

    Phase 3 starts only after the roadmap is defensible.

    Phase 03 · Improvement delivery · Planned

    Improve the system in evidence-led order.

    Phase 3 will implement the recommendations accepted at the end of Phase 2. It is not a general rewrite mandate: every change must trace back to a validated problem or opportunity, preserve required behavior, and produce evidence that the intended risk or cost has actually been reduced.

    The phase is deliberately not started. Its final scope, milestones, and estimates depend on the Phase 2 findings and recommendation decisions.

    Phase charter

    Delivery governed by findings and gates.

    Phase 3 converts accepted recommendations into small, reviewable changes while maintaining a usable system and an auditable account of progress.

    Primary question
    Can the generated baseline become a trustworthy and sustainable engineering foundation?
    Entry condition
    Phase 2 coverage, findings, recommendations, and ordering approved
    Unit of delivery
    One recommendation or independently valuable slice with explicit acceptance criteria
    Change policy
    Preserve required behavior; migrate deliberately; measure before and after
    Exit condition
    Accepted scope complete, quality gates satisfied, residual risks documented
    Decision output

    03

    Entry gate · Closed

    Implementation waits for the assessment.

    Starting broad modernization early would mix diagnosis with treatment, hide the original baseline, and risk optimizing components that a later architectural decision would replace. Small emergency fixes may be handled separately, but they do not silently open Phase 3.

    • Phase 2 assessment complete
    • Findings validated and dispositioned
    • Recommendations accepted and ordered
    • Regression baseline and ownership agreed

    Delivery principles

    Improve without losing the ability to explain why.

    Progress is defined by accepted outcomes and retired risk, not lines changed, technologies introduced, or the number of recommendations marked complete.

    Traceability

    Findings stay attached

    Every change identifies its recommendation, affected findings, acceptance criteria, and evidence.

    Incrementality

    Smallest valuable slice

    Large target states are decomposed into reversible milestones that leave the system coherent.

    Behavior

    Required outcomes remain protected

    Functional contracts, data meaning, and user workflows change only when the recommendation explicitly requires it.

    Measurement

    Before and after are comparable

    Performance, reliability, complexity, and operational claims use agreed baselines and repeatable measurements.

    Migration

    Transitions are first-class work

    Data, APIs, configuration, deployments, and rollback receive the same design attention as the end state.

    Restraint

    No architecture for its own sake

    New abstractions, services, libraries, or patterns must remove a demonstrated problem at acceptable cost.

    Expected outputs

    A changed system and a stronger evidence record.

    Implemented roadmap

    Accepted recommendations completed, deferred, or revised with decision history intact.

    Verified risk reduction

    Closed findings link to tests, measurements, migrations, or operational evidence.

    Updated architecture

    Current-state diagrams and decision records reflect what was actually delivered.

    Readiness assessment

    Residual blockers, accepted risks, operating limits, and next-phase options are explicit.

    Phase 03 · Delivery sequence

    Deliver in dependency-aware waves.

    The sequence below is a planning frame, not a pre-approved backlog. Phase 2 will determine which waves are needed, what belongs in each one, and where dependencies require a different order.

    Provisional sequence

    Stabilize, reshape, then optimize.

    Each wave must leave a tested and supportable system; later waves do not excuse unfinished earlier gates.

    1. 00
      Preparation

      Baselines and safety rails

      Confirm ownership, acceptance tests, measurements, migration rehearsal, rollback, and the first approved change packets.

      Unlocks reliable comparison and controlled delivery
    2. 01
      Protection

      Production and safety blockers

      Resolve unacceptable clinical, correctness, security, privacy, recovery, and data-integrity conditions.

      Required before readiness can advance
    3. 02
      Foundation

      Architecture and boundaries

      Reduce systemic coupling, clarify ownership, and establish the seams required for safe downstream changes.

      Prevents later work from reinforcing structural liabilities
    4. 03
      Resilience

      Data, performance, and operations

      Address measured bottlenecks, concurrency and consistency risk, observability gaps, capacity, deployment, and recovery.

      Improves predictable behavior under real operating conditions
    5. 04
      Sustainability

      Maintainability and developer experience

      Remove costly duplication and bulk, simplify change paths, align conventions, and improve feedback and documentation.

      Reduces the recurring cost of future delivery
    6. 05
      Readiness

      System validation and residual risk

      Re-run end-to-end evidence, close or accept remaining findings, update architecture, and determine the next posture.

      Produces the Phase 3 closure decision

    Unit of delivery

    Every change begins as a complete packet.

    A packet is ready only when implementation can begin without guessing at purpose, boundaries, proof, or rollback.

    Why

    Recommendation, linked findings, intended value, and consequences of doing nothing.

    What

    Scope, target state, preserved behavior, exclusions, dependencies, and migration path.

    Proof

    Acceptance criteria, required tests, measurements, review evidence, and operational checks.

    Safety

    Risk analysis, rollout controls, observability, rollback, data protection, and recovery.

    Ownership

    Responsible engineer, reviewers, stakeholders, decision authority, and follow-up owner.

    Closure

    Delivered evidence, changed assumptions, residual risk, documentation, and finding dispositions.

    Recommendation lifecycle

    Status follows evidence.

    1. AcceptedDirection approved
    2. ReadyPacket and prerequisites complete
    3. ActiveImplementation in progress
    4. ValidatingAcceptance and regression evidence running
    5. CompleteCriteria met and findings dispositioned

    At any point a recommendation may be blocked, revised, deferred, superseded, or rejected—with the reason retained.

    Phase 03 · Quality gates

    Completion requires proof, not confidence.

    Quality gates define the minimum evidence a change must produce before it can advance. The exact tests and measurements vary by recommendation, but no delivery can waive relevant safety, data, security, migration, or operational concerns by declaring them out of scope after implementation begins.

    Per-change gates

    Seven questions before “done.”

    Each gate is marked applicable or not applicable during planning; a not-applicable decision includes a reason.

    01

    Intent

    Do implementation and review agree with the accepted target state and scope?

    02

    Correctness

    Do focused and end-to-end tests protect required behavior, invariants, and failure cases?

    03

    Safety and security

    Have relevant clinical, privacy, authorization, misuse, and sensitive-data risks been reviewed?

    04

    Data and migration

    Are schema, compatibility, conversion, concurrency, rollback, retention, and recovery demonstrated?

    05

    Performance

    Are affected latency, throughput, resource, query, and capacity claims measured against the baseline?

    06

    Operations

    Can the change be observed, deployed, supported, diagnosed, rolled back, and recovered safely?

    07

    Maintainability

    Are ownership, documentation, architecture records, tests, and future change paths clearer than before?

    Phase-level gates

    Local success must add up to system confidence.

    Wave gate

    All required change packets complete; wave-wide regression, migration, operational, and architecture evidence reviewed.

    Readiness gate

    Production blockers resolved or explicitly accepted by the proper authority; operating limits and residual risks current.

    Closure gate

    Accepted Phase 3 scope dispositioned, final architecture and evidence published, and next-phase decision recorded.

    Phase 03 · Progress record

    Track outcomes without rewriting history.

    Phase 3 progress will be reported against the accepted roadmap. It will not change the Phase 1 record or retroactively improve Phase 2 scores; instead, completed work will link to the findings it addresses and the evidence that supports a new current-state assessment.

    —Delivery progress

    Current status

    No delivery work is authorized yet.

    Progress remains empty until Phase 2 approves the scope and creates the first ready change packets. This avoids counting preparatory ideas, unrelated commits, or Phase 1 work as Phase 3 improvement.

    Not started

    Future measures

    Progress will describe value and remaining risk.

    Counts support governance, but the narrative must explain what changed and whether the system is actually safer or easier to sustain.

    —Accepted recommendations

    The approved Phase 3 denominator, including deferred and rejected decisions.

    —Validated complete

    —Findings addressed

    —Blockers remaining

    —Change failure

    Rollback, escaped regression, migration issue, or gate failure trends during delivery.

    —Residual risk

    Accepted and deferred exposure carried into the final readiness decision.

    Changes in direction stay visible.
